## 2. Результат работы

Завершена реализация полнофункционального собственного CRUD REST API на Express 5 и выполнена его интеграция с React-клиентом:
1. Реализованы операции изменения данных:
   - `POST /api/tasks` — создание новой задачи с назначением сервером уникального `id` и статуса `completed: false`, заголовок `Location: /api/tasks/:id`, статус `201 Created`.
   - `PATCH /api/tasks/:id` — частичное изменение задачи (только переданные поля), статус `200 OK`.
   - `DELETE /api/tasks/:id` — удаление задачи, статус `204 No Content` без тела ответа.
2. Реализована строгая валидация тела запроса (`src/task-validation.js`):
   - проверка типов данных (JSON-объект, строковое название 1–100 символов, допустимый приоритет, числовой существующий `categoryId`);
   - запрет передачи `id` и `completed` в теле `POST`-запроса;
   - запрет передачи `id` в теле `PATCH`-запроса;
   - отклонение неизвестных и небезопасных свойств (включая `__proto__`);
   - при ошибках валидации возвращается статус `400 VALIDATION_ERROR` со структурированным объектом `details`.
3. В хранилище (`src/store.js`):
   - методы `createTask`, `updateTask`, `deleteTask` работают иммутабельно и возвращают изолированные копии объектов;
   - счётчик `nextId` монотонно возрастает и не уменьшается при удалении задач.
4. Проведена полная интеграция с React-клиентом ПР8 (через хук `useTaskData`):
   - после подтверждённой записи автоматически выполняется повторный `GET`;
   - блокировка повторных кликов через `mutationLockRef` исключает дублирование записей;
   - при сетевом сбое или 400 ошибке черновик формы сохраняется, а блокировка кнопок снимается.

### 3.1. Сценарий интеграции
1. **Начальное условие:** `q=провер`.
   - Выборка `GET /api/tasks?q=%D0%BF%D1%80%D0%BE%D0%B2%D0%B5%D1%80` возвращает 2 задачи (id: 7 и id: 16), `meta.total = 2`.
2. **Создание задачи через POST:**
   - Запрос: `POST /api/tasks`
   - Тело:
     ```json
     {
       "title": "ПРОВЕРИТЬ собственный API",
       "priority": "high",
       "categoryId": 2
     }
     ```
   - Ответ: статус `201 Created`, заголовок `Location: /api/tasks/35`, тело:
     ```json
     {
       "data": {
         "id": 35,
         "title": "ПРОВЕРИТЬ собственный API",
         "completed": false,
         "priority": "high",
         "categoryId": 2
       }
     }
     ```
   - Проверка выборки `q=провер`: найдено 3 задачи (id: 7, 16, 35).
3. **Переименование через PATCH:**
   - Запрос: `PATCH /api/tasks/35`
   - Тело:
     ```json
     {
       "title": "Готово"
     }
     ```
   - Ответ: статус `200 OK`, задача обновлена: `title: "Готово"`, `completed: false`, `priority: "high"`, `categoryId: 2`.
   - Проверка выборки `q=провер`: задача id 35 больше не содержит подстроку «провер» и исчезает из выборки. Найдено ровно 2 задачи (id: 7 и 16).
4. **Прямой неверный запрос:**
   - Запрос: `POST /api/tasks` с телом `{"title": "   ", "priority": "urgent", "categoryId": 999}`.
   - Ответ: статус `400 Bad Request` (`VALIDATION_ERROR`):
     ```json
     {
       "error": {
         "code": "VALIDATION_ERROR",
         "message": "Данные задачи не прошли проверку.",
         "details": {
           "title": "Название должно содержать от 1 до 100 символов.",
           "priority": "Приоритет должен быть \"low\", \"medium\" или \"high\".",
           "categoryId": "Категория должна быть существующим числовым идентификатором."
         }
       }
     }
     ```
   - Сервер отклонил запрос, массив данных не изменился, счётчик `nextId` не израсходован.

## 5. Контрольные вопросы

1. **Чем отличаются форматы валидации POST и PATCH?**  
   Для `POST` поля `title`, `priority`, `categoryId` являются строго обязательными, а передача `id` и `completed` запрещена (сервер сам генерирует id и выставляет `completed: false`). Для `PATCH` обязательно передать хотя бы одно поле из `title`, `priority`, `categoryId`, `completed`, отсутствующие поля не затрагиваются, а передача `id` запрещена.

2. **Зачем проверять заголовок `Content-Type: application/json`?**  
   Это предотвращает передачу некорректно закодированных данных или атак типа CSRF через стандартные HTML-формы (которые используют `application/x-www-form-urlencoded` или `multipart/form-data`).

3. **Почему после DELETE возвращается статус 204 No Content без тела ответа?**  
   По стандарту HTTP статус 204 указывает на то, что запрос успешно выполнен, но в теле ответа клиенту не передаётся полезная нагрузка (0 байт), поскольку удалённый ресурс более не существует.

4. **Почему счётчик `nextId` не уменьшается при удалении задачи?**  
   Уменьшение счётчика привело бы к тому, что вновь созданная задача получила бы идентификатор недавно удалённой записи. Это вызывает конфликты кэша на клиенте, ложные совпадения в логах и проблемы согласованности данных.

5. **Как middleware `requireTask(store)` защищает от лишней работы?**  
   Он проверяет корректность `id` и наличие задачи в базе до того, как начнётся парсинг и валидация тела запроса `PATCH`. Если задача с таким `id` уже удалена, сервер немедленно вернёт 404 без лишней нагрузки на CPU.
