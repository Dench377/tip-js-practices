## 2. Результат работы

React-приложение переведено с локального состояния в памяти на взаимодействие с реальным HTTP API:
1. Задачи и категории запрашиваются с сервера через асинхронные запросы (`GET /api/tasks`, `GET /api/categories`).
2. Фильтры передаются серверу в query-параметрах (`?q=...&completed=...&priority=...&categoryId=...`), сервер выполняет фильтрацию и возвращает метаданные `meta.total`.
3. Создание (`POST`), редактирование (`PATCH`), смена статуса (`PATCH`) и удаление (`DELETE`) выполняются через серверные эндпоинты с подтверждением.
4. Разработан кастомный хук `useTaskData`, инкапсулирующий работу с жизненным циклом React, эффектами `useEffect`, отменой устаревших запросов через `AbortController`, защитой от двойных кликов и сохранением последнего снимка при сбоях сети.

## 3. Архитектура хука `useTaskData`

Хук `src/hooks/useTaskData.js` решает ключевые проблемы асинхронного интерфейса:

### 3.1. Загрузка и отмена запросов (Race Conditions & StrictMode)
При смене фильтров `filters` или вызове `refresh()` запускается `useEffect`:
- Создаётся экземпляр `AbortController`.
- При быстром вводе текста в поиск предыдущий незавершённый запрос немедленно отменяется (`abortController.abort()`).
- В режиме разработки React 18/19 `StrictMode` монтирует компонент дважды; благодаря отмене первого пробного запроса и флагу активности `active` запоздавшие ответы не затирают актуальные данные.

### 3.2. Блокировка повторных кликов (Double Submit Prevention)
Для предотвращения дублирования записей при двойном клике по кнопке «Сохранить» используется синхронный `useRef`:
```javascript
if (mutationLockRef.current) {
  return false;
}
mutationLockRef.current = true;
setPending(true);
```
Два одновременных синхронных вызова создают ровно один сетевой запрос; второй вызов мгновенно возвращает `false`.

### 3.3. Разделение ошибок (Error Boundaries)
Ошибки чтения (`error`) и ошибки записи (`mutationError`) хранятся раздельно:
- Если падает `saveTask` (например, 400 Validation Error), это фиксируется в `mutationError`, форма не сбрасывает введённые пользователем данные, а текущий отображаемый список задач остаётся неповреждённым.
- При успешной мутации `saveTask` возвращает `true` и автоматически инициирует повторный `GET` для синхронизации с базой данных сервера.

## 6. Контрольные вопросы

1. **Почему в React для асинхронных запросов используется `useEffect`?**  
   Запросы по сети являются побочными эффектами (side effects), которые не должны вызываться непосредственно в теле рендера компонента. `useEffect` выполняет запрос после того, как компонент смонтирован или обновился, и предоставляет механизм очистки (cleanup).

2. **Как работает отмена запроса через `AbortController`?**  
   Создаётся объект `const controller = new AbortController()`, его свойство `controller.signal` передаётся в параметры вызова `fetch(url, { signal })`. При вызове `controller.abort()` браузер немедленно прекращает сетевое соединение, а промис отклоняется с исключением `DOMException: The user aborted a request`.

3. **Что такое «состояние гонки» (Race Condition) при поиске?**  
   Если пользователь быстро вводит «а», затем «аб», уходят два запроса. Сервер может ответить на второй запрос быстрее, чем на первый (например, из-за сетевой задержки). Если не отменять первый запрос, устаревший ответ на «а» придёт позже и перезапишет актуальный результат для «аб».

4. **Зачем нужен `useRef` для блокировки повторной мутации?**  
   Обновление состояния через `useState` является асинхронным и применяется только на следующем рендере. Если пользователь сделает двойной клик быстрее, чем произойдёт рендер, два обработчика прочитают старое значение `pending = false`. Мутация через `useRef.current = true` происходит синхронно и мгновенно блокирует второй клик.

5. **Почему после успешного `POST /api/tasks` выполняется повторный `GET`?**  
   Сервер может присваивать новые поля, генерировать id, форматировать дату, а также текущий список может зависеть от сортировки и пагинации на сервере. Повторный `GET` гарантирует полную синхронизацию клиента с состоянием сервера.
