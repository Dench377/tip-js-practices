## 2. Результат работы

Разработано полнофункциональное React-приложение для управления задачами:
1. Выводится список задач и привязанные названия категорий (справочник `categories`).
2. Доступно создание новых задач и редактирование существующих с клиентской валидацией полей (название 1–100 символов, допустимый приоритет, валидная категория).
3. Реализовано переключение статуса выполнения (чекбокс) и удаление задач с подтверждением через `window.confirm`.
4. Реализована совместная фильтрация по тексту `q` (регистронезависимый поиск), статусу `completed`, приоритету `priority` и категории `categoryId`.
5. Отображается сводная статистика всего набора (всего, выполнено, активно) и число найденных задач по текущему фильтру.
6. При пустой выборке выводится информативное сообщение.
7. Данные хранятся в памяти страницы (`useState` в корневом компоненте `App`). При перезагрузке страницы восстанавливается исходный набор данных из `data.js` — это архитектурное свойство ПР7, так как подключение внешнего HTTP API и базы данных относится к ПР8–ПР12.

## 3. Компоненты и управление состоянием

### 3.1. Владельцы состояния (State Ownership)
- **`App.jsx`** — владелец глобального состояния приложения:
  - `tasks`: массив задач (инициализируется копией `initialTasks`).
  - `filters`: объект параметров фильтрации (по умолчанию вариант 7: `{ q: 'провер', completed: '', priority: '', categoryId: '' }`).
  - `editingId`: идентификатор редактируемой задачи или `null` (если форма в режиме создания).
- **`TaskForm.jsx`** — владелец локального состояния черновика:
  - `title`, `priority`, `categoryId` — управляемые поля ввода.
  - `errors` — объект ошибок валидации полей `{ title?, priority?, categoryId? }`.
  - `generalError` — общее сообщение об ошибке (например, при попытке сохранить удалённую задачу).

### 3.2. Направление передачи данных (Data Flow)
- Данные передаются **сверху вниз** через props:
  - `App` → `TaskStats` (`stats`).
  - `App` → `TaskFilters` (`filters`, `categories`).
  - `App` → `TaskForm` (`categories`, `initialTask`).
  - `App` → `TaskList` (`tasks`, `categories`) → `TaskItem` (`task`, `categoryName`).
- Действия передаются **снизу вверх** через функции обратного вызова (callbacks):
  - `TaskItem` вызывает `onToggle(id)`, `onEdit(id)`, `onDelete(id)`.
  - `TaskFilters` вызывает `onChange(nextFilters)`.
  - `TaskForm` вызывает `onSave(value)` и `onCancel()`.

### 3.3. Производные данные (Derived State)
Видимый список `visibleTasks`, статистика `stats` и редактируемая задача `editingTask` **не дублируются в `useState`**, а вычисляются непосредственно во время рендера:
```jsx
const visibleTasks = selectTasks(tasks, filters);
const stats = getTaskStats(tasks);
const editingTask = editingId !== null ? tasks.find(t => t.id === editingId) ?? null : null;
```
Это предотвращает рассинхронизацию интерфейса и исключает избыточные рендеры.

### 3.4. Сброс формы через ключ (key)
Для чистого переключения между созданием и редактированием форма пересоздаётся через ключ:
```jsx
<TaskForm
  key={editingId ?? 'new'}
  categories={categories}
  initialTask={editingTask}
  onSave={handleSave}
  onCancel={handleCancelEdit}
/>
```
При смене `editingId` старый экземпляр `TaskForm` размонтируется, а новый монтируется со свежими начальными значениями.

## 7. Контрольные вопросы

1. **Чем JSX отличается от строки HTML?**  
   JSX — это синтаксический сахар для вызовов функций JavaScript (компилируется в `React.createElement` или функции JSX runtime). JSX является строго типизированным выражением внутри JS, поддерживает полную выразительность языка, автоматическое экранирование для защиты от XSS и работу с объектами событий React SyntheticEvent.

2. **Чем props отличаются от состояния (state)?**  
   `props` передаются компоненту извне от родителя и являются неизменяемыми (read-only) для компонента-получателя. `state` создаётся и управляется внутри самого компонента через `useState` и хранит изменяемые данные, определяющие рендеринг.

3. **Почему изменение обычной переменной не заменяет `useState`?**  
   Обычная локальная переменная пересоздаётся при каждом вызове функции компонента и теряет значение между рендерами. Изменение обычной переменной не уведомляет React о необходимости повторного рендеринга (re-render) компонента.

4. **Когда требуется функциональная форма обновления состояния (`setCount(prev => prev + 1)`)?**  
   Когда новое состояние зависит от предыдущего, либо когда несколько обновлений происходят в рамках одной очереди (batching), а также внутри замыканий и асинхронных функций, где прямое чтение переменной состояния может вернуть устаревшее значение (stale state).

5. **Почему нельзя менять объект задачи внутри поверхностной копии массива?**  
   Поверхностная копия `[...tasks]` создаёт новый массив, но элементы внутри него ссылаются на те же самые объекты в памяти. Изменение `tasksCopy[0].completed = true` мутирует исходный объект, нарушая контракт чистых функций и препятствуя корректной оптимизации React (который сравнивает объекты по ссылкам).

6. **Для чего списку стабильный `key` и почему индекс массива здесь не подходит?**  
   `key` позволяет алгоритму согласования (reconciliation) React сопоставлять элементы виртуального DOM между рендерами. Если использовать индекс массива, то при удалении или вставке элементов в середину списка индексы сдвигаются, что приводит к багам с сохранением локального состояния дочерних компонентов (например, фокус или черновики полей) и лишним перерисовкам.

7. **Почему видимая выборка и статистика не хранятся в отдельных состояниях?**  
   Они являются производными (вычисляемыми) данными от массива `tasks` и объекта `filters`. Дублирование их в `useState` потребовало бы ручной синхронизации после каждого добавления, удаления или изменения, что ведёт к багам рассинхронизации.

8. **Как дочерний компонент сообщает родителю о действии?**  
   Родитель передаёт дочернему компоненту функцию обратного вызова (callback) через `props` (например, `onToggle={handleToggle}`). Дочерний компонент вызывает эту функцию при наступлении события (например, `onClick={() => onToggle(task.id)}`).

9. **Что делает поле формы управляемым (controlled)?**  
   Поле становится управляемым, когда его отображаемое значение задаётся через prop `value` из состояния React, а любое изменение перехватывается через `onChange` и обновляет это состояние. Таким образом, React является единым источником правды («single source of truth»).

10. **Почему `categoryId` из `<select>` требует преобразования?**  
    HTML-элемент `<select>` всегда возвращает строковое значение (`event.target.value` — это строка, например `"2"`). В модели данных задачи `categoryId` должен храниться как число (`number`).

11. **Как меняется состояние формы при изменении её ключа (`key`)?**  
    При изменении значения атрибута `key` React полностью демонтирует старый экземпляр компонента и монтирует новый с нуля. Это автоматически сбрасывает все внутренние состояния `useState` до начальных значений `initialTask`.

12. **Почему подтверждение удаления (`confirm`) не помещается внутрь функции обновления состояния?**  
    В React (особенно в режиме `StrictMode`) функции обновления состояния должны быть строго чистыми и могут вызываться движком повторно. Вызов модальных окон или сайд-эффектов внутри `setTasks(prev => ...)` приводит к повторному показу диалога подтверждения.

13. **Как отличить отсутствие задач от отсутствия совпадений фильтра?**  
    По длине массивов: если `tasks.length === 0`, значит в хранилище вообще нет задач; если `tasks.length > 0`, но `visibleTasks.length === 0`, значит задачи есть, но ни одна не подошла под текущие фильтры.

14. **Что проверяет `npm test` и чего он не проверяет?**  
    `npm test` запускает 28 проверок предметной логики (`domain/task-service.js`): валидацию, фильтрацию, подсчёт статистики, чистые мутации без побочных эффектов. Он **не** проверяет рендеринг React-компонентов в DOM, стилизацию CSS и обработку пользовательских кликов мыши.

15. **Какие части приложения потребуется изменить для подключения API в ПР8?**  
    Потребуется заменить синхронные вызовы `addTask`, `updateTask`, `removeTask` в памяти на асинхронные HTTP-запросы (`fetch`) через специализированный хук `useTaskData`, добавить обработку состояний ожидания (`pending`, `loading`) и сетевых ошибок.
