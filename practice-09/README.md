## 2. Результат работы

Самостоятельно реализован полнофункциональный серверный модуль на базе Express 5:
1. Реализована обработка запросов:
   - `GET /api/health` — проверка доступности сервиса.
   - `GET /api/categories` — получение справочника категорий с метаданными `meta.total`.
   - `GET /api/tasks` — получение списка задач с поддержкой комплексной фильтрации (`completed`, `priority`, `categoryId`, `q`).
   - `GET /api/tasks/:id` — получение детальной информации о задаче по идентификатору.
2. Реализована строгая валидация входящих query-параметров (`src/validation.js`):
   - запрещены неизвестные параметры (`unknown=1` -> 400 `INVALID_QUERY`);
   - запрещены повторяющиеся параметры (`q=a&q=b` -> 400 `INVALID_QUERY`);
   - проверены границы длины поисковой строки `q` (до 100 символов);
   - проверена целостность числовых ID категорий и задач (отклонение ведущих нулей `'01'`, дробных чисел, строк).
3. Настроена маршрутизация с методом `router.all` для известных путей, возвращающая статус `405 METHOD_NOT_ALLOWED` и заголовок `Allow: GET, HEAD, OPTIONS`.
4. Для неизвестных путей настроен возврат статуса `404 ROUTE_NOT_FOUND`.
5. Исходные данные хранятся изолированно и не мутируют при любых операциях чтения.

## 3. Архитектура и разделение ответственности

Проект разделён на слабо связанные слои:
- **`src/validation.js`** — слой парсинга и валидации входных данных (`parsePositiveId`, `parseFilters`).
- **`src/task-service.js`** — сервисный слой предметной логики (`selectTasks`, `findTask`), не зависящий от Express и сети.
- **`src/store.js`** — фабрика хранилища данных процесса в памяти (`createStore`).
- **`src/routes.js`** — Express-маршрутизатор (`createRouter`), связывающий HTTP-запросы с валидатором и хранилищем.
- **`src/errors.js`** — класс ошибок `ApiError` и централизованный middleware `errorHandler`, гарантирующий единообразный формат JSON `{ error: { code, message, details? } }` и скрывающий системные стектрейсы при 500 ошибках.

## 6. Контрольные вопросы

1. **Что такое middleware в Express и какую роль он играет?**  
   Middleware — это функция с сигнатурой `(req, res, next)`, имеющая доступ к объектам запроса, ответа и следующей функции в конвейере. Используется для сквозных задач: добавление заголовков CORS, логирование, разбор тела JSON, проверка авторизации и централизованная обработка ошибок.

2. **Чем отличается обработка ошибок через middleware с 4 аргументами `(err, req, res, next)`?**  
   Express распознаёт обработчик ошибок именно по наличию четырёх параметров. Когда любой маршрут или middleware вызывает `next(error)`, Express пропускает все оставшиеся обычные маршруты и напрямую передаёт управление первому в цепочке middleware с 4 аргументами.

3. **Почему для путей `/health`, `/categories`, `/tasks`, `/tasks/:id` используется статус 405, а не 404?**  
   Статус 404 означает, что запрашиваемый URI не существует в системе. Если же ресурс существует, но обращение выполнено с неподдерживаемым HTTP-методом (например, `POST /api/health`), стандарт HTTP требует возвращать статус 405 Method Not Allowed вместе с заголовком `Allow`, перечисляющим допустимые методы (`GET, HEAD, OPTIONS`).

4. **Зачем проверять `Number.isSafeInteger` при парсинге ID?**  
   В JavaScript числа с плавающей точкой IEEE 754 могут безопасно и точно представлять целые числа только в диапазоне от `-(2^53 - 1)` до `2^53 - 1` (`9007199254740991`). Числа сверх этого предела теряют младшие разряды, что приводит к ложным совпадениям ID в базе данных.

5. **Почему параметры поиска не должны мутировать исходный массив данных?**  
   Операции чтения (GET) по стандарту HTTP должны быть безопасными (safe) и идемпотентными (idempotent). Мутация исходного массива привела бы к потере данных для последующих запросов других пользователей или параллельных сессий.
