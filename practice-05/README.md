## Эксперимент с очередями выполнения

До запуска `npm run example:order` составлен прогноз порядка вывода сообщений на основе модели фаз Event Loop (синхронный стек → микрозадачи Promise → макрозадачи таймеров):

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | `A` → `B` → `C` → `D` → `E` → `F` | `A`, `B`, `C` выполняются синхронно в главном потоке вызовов. Вызовы `then` и `await` ставят микрозадачи в microtask queue (`D`, `E`). Коллбэк `setTimeout` попадает в очередь макрозадач (timer phase) и выполняется последним (`F`). |
| Фактический результат | `A` → `B` → `C` → `D` → `E` → `F` | `A: синхронный код`<br>`B: начало async-функции`<br>`C: конец синхронного кода`<br>`D: обработчик Promise`<br>`E: продолжение после await`<br>`F: задача таймера` |

Анализ:
- **Синхронный код:** `A` (до вызова функций), `B` (синхронная часть тела `async`-функции до первого ключевого слова `await`), `C` (код сразу после вызова `async`-функции в основном скрипте).
- **Очередь микрозадач (Microtask Queue):** `D` (колбэк `.then()` от `Promise.resolve()`) и `E` (возобновление выполнения тела `async`-функции после урегулирования `await Promise.resolve()`). Микрозадачи опустошаются средой V8 сразу после завершения текущего синхронного стека до перехода к следующей макрозадаче.
- **Таймер с задержкой 0:** коллбэк `setTimeout(..., 0)` регистрируется в очереди задач таймеров Event Loop. Нулевой таймаут означает не немедленное исполнение, а готовность к выполнению на следующей итерации цикла событий только после полной очистки очереди микрозадач.
- **Если удалить один из Promise:** при удалении обработчика `D` метка `E` выполнится первой из микрозадач, но таймер `F` всё равно будет выполнен строго после неё.

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Предоставленный сервер учебной инфраструктуры Node.js HTTP. Обрабатывает эндпоинты `/health`, `/tasks`, `/categories`, CORS и отладочные сценарии. |
| `src/api-client.js` | Базовый сетевой транспорт: нормализация URL через `buildUrl`, валидация параметров, выполнение запросов через `fetchFn`, таймауты (`AbortSignal.timeout`), внешняя отмена (`AbortSignal.any`) и классификация ошибок в иерархию `ApiError`. Не содержит предметной логики. |
| `src/task-api.js` | Предметный модуль приложения: валидация фильтров (`ALLOWED_FILTERS`), вызов эндпоинтов задач и категорий, проверка соответствия схемы данных контракту (`isTask`, `isCategory`, уникальность `id`, `meta.total`) и параллельная загрузка `loadInitialData`. |
| `src/variant.js` | Конфигурация индивидуального варианта студента (номер 7 и параметры фильтрации `{ q: "провер" }`). |
| `src/main.js` | Точка входа клиентского консольного приложения: выполнение контрольного запроса, замер времени ответа и вывод таблицы данных. |

**Архитектурные решения:**
- `fetchFn` передаётся параметром в фабрику `createApiClient` (Dependency Injection), что позволяет изолированно тестировать клиент с поддельными моками `Response` без обращения к реальной сети.
- HTTP-ошибки (`status >= 400`) отделены от сетевых ошибок: ответ сервера со статусом 404 или 500 означает успешную сетевую доставку, поэтому Promise от `fetch` не отклоняется, а статус проверяется явно через `!response.ok`.
- Валидация JSON после разбора необходима, так как синтаксически корректный JSON может содержать произвольную структуру или искажённые поля, не соответствующие доменной модели.

## Доменный модуль задач

| Вызов | Результат |
|---|---|
| `getTasks()` | 12 задач, идентификаторы `[1, 4, 7, 10, 13, 16, 19, 22, 25, 28, 31, 34]`, `meta.total = 12` |
| `getTasks({ completed: false, priority: "high" })` | 3 задачи, идентификаторы `[4, 13, 34]`, `meta.total = 3` |
| `getTaskById(25)` | Объект `{ id: 25, title: "Исправить обработку ошибок", completed: true, priority: "high", categoryId: 2 }` |
| `getCategories()` | 3 категории: `[ { id: 1, name: "Учёба" }, { id: 2, name: "Проект" }, { id: 3, name: "Инфраструктура" } ]` |
| `loadInitialData({ completed: true })` | 5 задач (`[1, 10, 16, 25, 31]`), 3 категории, `meta.total = 5` |

Правила валидации доменной модели:
- `isTask`: положительный безопасный целое `id > 0`, непустая строка `title` (1–100 символов), `completed` — strictly boolean, `priority` строго входит в `low`, `medium`, `high`, `categoryId` — положительное целое.
- `isCategory`: положительный `id > 0`, непустая строка `name` (1–100 символов).
- Проверка уникальности: идентификаторы задач и категорий проверяются через коллекцию `Set`; повторение приводит к выбросу `ApiError` с `kind: "invalid-response"`.
- Проверка целостности метаданных: значение `meta.total` строго сравнивается с `data.length`.

## Последовательная и параллельная загрузка

Сравнение двух способов загрузки задач и категорий с искусственной задержкой `/api/debug/delay?ms=150`:

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение |
|---|---:|---:|---:|---|
| Два последовательных `await` | 318.4 | 312.1 | 314.9 | Время равно сумме двух задержек ($150 + 150 = 300$ мс плюс накладные расходы HTTP) |
| Параллельный `Promise.all` | 159.2 | 156.8 | 158.4 | Оба запроса инициированы одновременно; общее время определяется максимальным из двух ($~150$ мс) |

Вывод: независимые HTTP-ресурсы должны запрашиваться параллельно через `Promise.all`, что сокращает сетевое время ожидания почти вдвое.

## Отладка

Точки останова установлены в модуле `src/api-client.js`:
1. **Точка 1 (перед `fetchFn`):** проверка сформированного URL (`http://127.0.0.1:5505/api/tasks?q=%D0%BF%D1%80%D0%BE%D0%B2%D0%B5%D1%80`), опций запроса (`method: "GET"`, `headers.Accept: "application/json"`) и объединённого сигнала `AbortSignal`.
2. **Точка 2 (после получения `Response`):** фиксация `response.status === 200`, `response.ok === true`, `response.headers.get("content-type") === "application/json; charset=utf-8"`.
3. **Точка 3 (перед `response.json()`):** проверка состояния потока ответа (тело ещё не прочитано).
4. **Точка 4 (обработка ошибки):** при запросе задачи `999` зафиксированы `response.status === 404`, `response.ok === false`. Тело ошибки разобрано в `{ error: { code: "TASK_NOT_FOUND", message: "Задача с id 999 не найдена.", details: { id: 999 } } }`, сформирован объект `ApiError` с полями `kind: "http"`, `status: 404`, `code: "TASK_NOT_FOUND"`.

## Дополнительное задание (Вариант А: Частичный результат через `Promise.allSettled`)

В модуле `src/task-api.js` реализована функция `loadInitialDataSettled(filters = {})`:
```javascript
async function loadInitialDataSettled(filters = {}) {
  const [tasksSettled, categoriesSettled] = await Promise.allSettled([
    getTasks(filters),
    getCategories(),
  ]);

  return {
    tasks: tasksSettled.status === "fulfilled" ? tasksSettled.value.tasks : null,
    meta: tasksSettled.status === "fulfilled" ? tasksSettled.value.meta : null,
    categories: categoriesSettled.status === "fulfilled" ? categoriesSettled.value : null,
    errors: {
      tasks: tasksSettled.status === "rejected" ? tasksSettled.reason : null,
      categories: categoriesSettled.status === "rejected" ? categoriesSettled.reason : null,
    },
  };
}
```

Проверки:
1. **Успех обоих запросов:** возвращаются списки задач, категорий, метаинформация, поле `errors` содержит `{ tasks: null, categories: null }`.
2. **Сбой запроса задач при доступных категориях:** задачи равны `null`, категории успешно заполнены, `errors.tasks` содержит объект `ApiError`. Интерфейс может отобразить список категорий и изолированное сообщение об ошибке задач.
3. **Сбой запроса категорий при доступных задачах:** задачи и метаданные успешно возвращены, категории равны `null`, `errors.categories` содержит причину отказа. Приложение сохраняет базовую функциональность отображения задач.
