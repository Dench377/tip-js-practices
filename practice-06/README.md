## 1. Цель работы

Связать графический интерфейс браузерного веб-приложения с учебным RESTful HTTP API, организовать предсказуемое управление асинхронными состояниями интерфейса (`loading`, `ready`, `empty`, `error`), реализовать пессимистическую модель обновления данных на сервере и обеспечить защиту от состояния гонки (race conditions) при смене фильтров с помощью `AbortController` и счётчика последовательности запросов.

## 3. Реализация

### 3.1. HTTP-клиент (`src/api-client.js`)

Общий HTTP-клиент реализован в виде фабрики `createApiClient({ baseUrl, fetchFn, timeoutMs })`:
- Валидирует входную конфигурацию: протокол `http:`/`https:`, отсутствие query/hash в `baseUrl`, положительный таймаут.
- Функция `buildUrl(baseUrl, path, query)` чисто формирует абсолютный URL, добавляя только непустые строковые и логические параметры через `URLSearchParams`.
- Поддерживает методы: `GET`, `POST`, `PATCH`, `DELETE`. Запрещает передачу тела для `GET`-запросов.
- Заголовок `Accept: application/json` добавляется ко всем запросам. При наличии непустого тела объект сериализуется в JSON с выставлением заголовка `Content-Type: application/json`.
- Для ответа со статусом `204 No Content` возвращается `null` без попытки вызова `response.json()`.
- Статус ошибки сервера проверяется до валидации заголовка `Content-Type`, что исключает маскирование HTTP-ошибок (например, 502 Bad Gateway в text/plain) ошибками некорректного типа контента.
- Классифицирует ошибки в специализированный класс `ApiError` по видам (`kind`):
  - `http` — ошибки со статусами `4xx`/`5xx` с разбором структурированного JSON-конверта сервера;
  - `network` — сетевой сбой, потеря связи или отказ сервера;
  - `timeout` — истечение времени ожидания ответа сервера (`AbortSignal.timeout`);
  - `aborted` — принудительная отмена запроса клиентом (`AbortSignal.any`);
  - `invalid-response` — некорректный `Content-Type` или повреждённый JSON.

### 3.2. Доменный API (`src/task-api.js`)

Модуль `createTaskApi(client)` инкапсулирует операции над сущностями «Задача» (`Task`) и «Категория» (`Category`):
- `getTasks(filters, { signal })` — нормализует и валидирует фильтры (`completed`, `priority`, `categoryId`, `q`), отправляет `GET /api/tasks`, валидирует схему массива задач через предикат `isTask`.
- `getTaskById(id, { signal })` — выполняет `GET /api/tasks/:id` с валидацией целого положительного ID.
- `getCategories({ signal })` — выполняет `GET /api/categories`, проверяет структуру справочника через `isCategory`.
- `loadInitialData(filters, { signal })` — параллельно (`Promise.all`) загружает задачи и категории.
- `createTask(draft, { signal })` — выполняет `POST /api/tasks` со статусом `201 Created`.
- `updateTask(id, changes, { signal })` — выполняет частичное обновление `PATCH /api/tasks/:id`.
- `setTaskCompleted(id, completed, { signal })` — выполняет `PATCH /api/tasks/:id` с полем `{ completed }`.
- `deleteTask(id, { signal })` — выполняет `DELETE /api/tasks/:id`, строго ожидает `204 No Content` (`null`).
- `resetDemoData({ signal })` — восстанавливает исходный тестовый набор через `POST /api/debug/reset`.

### 3.3. Состояния интерфейса (`src/app-controller.js`, `src/dom-app.js`)

Контроллер координирует 4 взаимоисключающих состояния списка задач:
1. `loading`: атрибут `aria-busy="true"` на панели списка, сообщение «Загрузка задач…», список скрыт.
2. `ready`: непустой список карточек, актуальный счётчик задач, `aria-busy="false"`, сообщение состояния скрыто.
3. `empty`: запрос успешен, но совпадений нет (сообщение «По выбранным условиям задач нет.»), список пуст, старые карточки удалены через `replaceChildren`.
4. `error`: ошибка сети или HTTP, отображается локализованное сообщение из `messageForError(error)` и кнопка «Повторить загрузку».

### 3.4. Изменение данных (Пессимистическая модель)

Все мутации выполняются строго по пессимистическому принципу:
```text
Действие пользователя → Блокировка кнопок (setMutationPending) → HTTP-запрос (POST/PATCH/DELETE) 
→ Успешный ответ сервера → Уведомление об успехе → Повторный GET /tasks с текущими фильтрами 
→ Перерисовка списка → Разблокировка кнопок
```
Сервер является единственным источником истины (`Single Source of Truth`). Данные не кэшируются в `localStorage`.

### 3.5. Защита от устаревшего ответа и гонок запросов

Для предотвращения перезаписи актуального интерфейса запоздавшим ответом от предыдущего запроса применён двойной барьер:
1. При каждом новом запросе активный `AbortController` предыдущего запроса вызывает `.abort()`.
2. Контроллер инкрементирует целочисленный счётчик последовательности `loadSequence`. Ответ применяется к интерфейсу только в том случае, если сохранённый при старте номер совпадает с текущим значением `loadSequence`. Ошибки вида `aborted` перехватываются и не показываются пользователю.

## 6. Ответы на контрольные вопросы

1. **Почему `fetch` обычно не отклоняет Promise при статусе 404 или 500?**<br>
   *Ответ:* Спецификация Fetch API разделяет ошибки транспортного уровня сети и HTTP-статусы приложения. Promise отклоняется только при невозможности выполнить сетевой обмен (DNS-сбой, отсутствие интернета, отказ соединения, CORS-блокировка, прерывание по `AbortSignal`). Статусы 404 (Not Found) или 500 (Internal Server Error) являются валидными HTTP-ответами, успешно полученными от сервера, поэтому `fetch` успешно разрешает Promise объектом `Response` со свойством `response.ok === false`.

2. **В каком порядке проверяются `response.ok`, статус 204, `Content-Type` и JSON?**<br>
   *Ответ:*
   1. Сначала проверяется `!response.ok` — если сервер вернул ошибку, формируется `ApiError` с типом `http` и статусом сервера, чтобы непредвиденные ответы (например, HTML-страница 502 Bad Gateway) не маскировались под ошибки парсинга.
   2. Далее проверяется `response.status === 204` — при отсутствии тела возвращается `null` до чтения потока.
   3. Затем проверяется заголовок `Content-Type` на наличие `application/json`.
   4. В конце выполняется разбор `await response.json()`.

3. **Чем `POST` в контракте работы отличается от `PATCH`?**<br>
   *Ответ:* `POST /api/tasks` предназначен для создания нового ресурса. Клиент передаёт тело без `id` и `completed`, сервер сам генерирует уникальный идентификатор, устанавливает начальный статус `completed: false`, возвращает статус `201 Created` и заголовок `Location`. `PATCH /api/tasks/:id` выполняет частичную модификацию существующего ресурса: клиент передаёт только изменяемые поля (например, `{ completed: true }`), сервер валидирует и применяет изменения, возвращая статус `200 OK`.

4. **Для чего сервер возвращает 201 и заголовок `Location`?**<br>
   *Ответ:* Статус `201 Created` в протоколе HTTP стандартизирует успешное создание нового ресурса на стороне сервера. Заголовок `Location` содержит абсолютный или относительный URI созданного ресурса (например, `/api/tasks/35`), позволяя клиенту сразу узнать канонический адрес новой сущности для последующих обращений.

5. **Почему у ответа 204 не вызывается `response.json()`?**<br>
   *Ответ:* HTTP-статус `204 No Content` гарантирует отсутствие тела в ответе. Метод `response.json()` пытается прочитать поток ответа и распарсить его как JSON; при пустом теле это приводит к генерации синтаксической ошибки `SyntaxError: Unexpected end of JSON input`.

6. **Когда браузер отправляет CORS preflight и почему `no-cors` не решает задачу?**<br>
   *Ответ:* Браузер отправляет предварительный `OPTIONS`-запрос (preflight), когда запрос не является «простым» (simple request): используются методы `PATCH` или `DELETE`, либо передаётся заголовок `Content-Type: application/json`. Режим `mode: "no-cors"` не решает проблему, так как он превращает ответ в «непрозрачный» (`opaque`), блокируя чтение статуса и тела ответа из JavaScript-кода (возвращает статус 0 и недоступный body).

7. **Чем `empty` отличается от `error` с точки зрения данных и интерфейса?**<br>
   *Ответ:* Состояние `empty` отражает успешный HTTP-запрос (200 OK), в результате которого сервер вернул корректный, но пустой массив данных (например, ни одна задача не соответствует критериям фильтрации). Это штатный сценарий работы. Состояние `error` возникает при невозможности получить данные (сбой сети, таймаут, 500, 404) и требует отображения сообщения об ошибке и кнопки повторной попытки.

8. **Почему `localStorage` больше не является источником задач?**<br>
   *Ответ:* В распределённых клиент-серверных архитектурах единственным источником истины (`Single Source of Truth`) выступает централизованный сервер/база данных. Использование `localStorage` привело бы к рассинхронизации данных между разными клиентами, вкладками и сессиями, а также к конфликтам версий. В ПР6 массив задач в клиенте — это лишь временный снимок последнего серверного ответа.

9. **Зачем повторно загружать список после успешной мутации?**<br>
   *Ответ:* Пессимистическая модель гарантирует абсолютную согласованность UI с сервером. Сервер может применять триггеры, бизнес-правила, менять сортировку или отказывать в мутации. Повторный `GET /tasks` с текущими активными фильтрами гарантирует, что задача появится или исчезнет из выборки строго в соответствии с актуальным серверным состоянием.

10. **Как возникает гонка двух запросов при быстрой смене фильтра?**<br>
    *Ответ:* Если пользователь последовательно применил фильтр А, а затем фильтр Б, в сеть отправляются два асинхронных запроса. Из-за вариативности сетевых задержек или разной сложности обработки на сервере запрос Б может завершиться за 50 мс, а запрос А — за 300 мс. Без мер защиты ответ от устаревшего запроса А прибудет позже и перезапишет актуальный результат запроса Б.

11. **Почему одного `AbortController` недостаточно для защиты от любого устаревшего результата?**<br>
    *Ответ:* Не все сетевые клиенты или слои кэширования мгновенно прерывают исполнение при срабатывании сигнала отмены; кроме того, ответ мог уже успеть поступить в очередь микротасок JS до вызова `.abort()`. Счётчик последовательности запросов (`sequence counter`) гарантирует, что даже если устаревший Promise успел разрешиться, его данные будут проигнорированы контроллером.

12. **Почему отмена запроса не показывается пользователю как ошибка?**<br>
    *Ответ:* Отмена предыдущего запроса при смене фильтра является штатным управляющим механизмом приложения, инициированным самим пользователем (переход к новому действию). Отображение баннера ошибки в этой ситуации дезориентирует пользователя и создаёт ложное впечатление о неисправности системы.

13. **Что проверяет клиент, а что обязан повторно проверять сервер?**<br>
    *Ответ:* Клиент выполняет предварительную валидацию формы для улучшения отзывчивости интерфейса (UX) и экономии сетевого трафика. Однако клиентскую среду невозможно контролировать (запросы можно отправить через Postman, cURL или подделать в DevTools), поэтому сервер обязан повторно проверять типы данных, длину строк, допустимость значений перечислений и существование связанных сущностей (`categoryId`).

14. **Зачем контроллеру зависимость `view`, переданная параметром?**<br>
    *Ответ:* Принцип инверсии зависимостей (Dependency Inversion) и слабой связанности (Decoupling) отделяет логику управления состоянием от деталей реализации DOM. Это позволяет тестировать контроллер в изолированном окружении Node.js с помощью мок-объектов без необходимости поднимать тяжеловесный DOM или эмулятор браузера.

15. **Почему серверный текст выводится через `textContent`?**<br>
    *Ответ:* Данные, полученные с сервера, считаются недоверенными (Untrusted Data). Использование `innerHTML` делает приложение уязвимым для атак межсайтового скриптинга (Stored/Reflected XSS), если в названии задачи окажется вредоносный HTML/JS-код (например, `<img src=x onerror="alert(1)">`). Свойство `textContent` экранирует специальные символы и вставляет данные строго как текст.
